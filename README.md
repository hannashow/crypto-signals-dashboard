# Market Signal Radar

用技術指標判斷追蹤標的目前偏多或偏空,提供 Streamlit 儀表板檢視,並在訊號變化時發送 LINE 通知。

追蹤範圍涵蓋加密貨幣現貨與股票永續合約。

**僅供參考,非投資建議。**

## 系統組成

| 元件 | 說明 |
|---|---|
| Streamlit 儀表板 | 隨時打開檢視所有標的的訊號、指標數值與 K 線圖 |
| LINE 通知 | 定時執行 `check_signals.py`,訊號變化時推播 |

兩者共用同一套計分邏輯([signals.py](signals.py)),但獨立運作 —— 儀表板掛掉不影響通知。

通知的觸發鏈為:

```
cron-job.org(台灣時間 8:37 ~ 23:37,每小時)
  → 呼叫 GitHub API 的 workflow_dispatch 端點
  → GitHub Actions 執行 check_signals.py
  → 符合條件則透過 LINE Messaging API 推播
```

夜間(台灣 00:00–08:00)不執行,避免睡眠時被打擾。

## 追蹤標的

資料來源為 OKX 公開 API,1 小時 K 線。標的清單定義在 [config.py](config.py) 的 `SYMBOLS`。

| 標的 | 類型 | LINE 通知 |
|---|---|---|
| BTC/USDT、ETH/USDT | 加密貨幣現貨,24 小時連續交易 | ✅ |
| MU、QQQ、MRVL、DRAM | 股票永續合約,追蹤美股但合約 24 小時交易 | ✅ |
| NVDA、TSLA、AAPL、GOOGL、COIN、SPCX | 股票永續合約 | ❌ 僅儀表板 |

`SYMBOLS` 是儀表板顯示的完整清單,`ALERT_SYMBOLS` 是其中會發 LINE 通知的子集。兩者分開是因為 LINE 免費額度每月僅 200 則 —— 標的越多通知越多,12 個標的全部通知估計每月約 400 則,會超量一倍。不通知的標的仍可隨時開儀表板查看,總覽表以 🔔 標示哪些會通知。

OKX 沒有 GOOG 與 GRMN 的合約。GOOGL 與 GOOG 是 Alphabet 的不同股別(GOOGL 有投票權),股價貼近,故以 GOOGL 替代。

# 計分規則

分數為正代表偏多、負代表偏空,絕對值越大訊號越強。計分分成兩個階段:先由四條價格規則累加,再由量能確認修正。

## 第一階段:價格規則(各 ±1 分)

每條規則獨立判斷,符合多方條件 +1、空方條件 -1、兩者皆不符合則 0 分。

| 規則 | 多方條件(+1) | 空方條件(−1) |
|---|---|---|
| **RSI(14)** | RSI < 30(超賣) | RSI > 70(超買) |
| **MACD(12/26/9)** | 黃金交叉:MACD 線由下往上穿越訊號線 | 死亡交叉:MACD 線由上往下穿越訊號線 |
| **EMA(20/50)** | 收盤價 > EMA20 > EMA50(多頭排列) | 收盤價 < EMA20 < EMA50(空頭排列) |
| **布林通道(20, 2σ)** | 收盤價 ≤ 下軌 | 收盤價 ≥ 上軌 |

MACD 是唯一需要比較前後兩根 K 棒的規則(判斷是否發生穿越),其餘三條只看最新一根。

## 第二階段:壓力支撐(±1 分)

價格接近日線級別的區間時給分。接近支撐區偏多(有機會獲得支撐),接近壓力區偏空。

| 條件 | 分數 |
|---|---|
| 現價落在支撐區內,或距其中心 1% 以內 | **+1** |
| 現價落在壓力區內,或距其中心 1% 以內 | **−1** |
| 附近沒有有效區間 | 0 |

### 壓力支撐規則的來源

壓力支撐區不是從 1 小時 K 線找的,而是另外抓**日線**計算,流程在 [levels.py](levels.py):

1. **找擺動高低點** —— 某根日線的高點若是前後各 3 根範圍內最高,即為擺動高點,低點同理。需要右側 K 棒才能確認轉折,故最新 3 根不產生擺動點
2. **聚成區間** —— 相距 1.5% 以內的轉折點視為同一區。比對基準是群組的第一個成員而非前一個,否則 A→B、B→C 各差一個容忍度時會不斷串聯,最後圈出涵蓋整段行情的無效區間
3. **篩選強度** —— 至少被測試 2 次才算有效,再取離現價最近的 6 個

現價之上為壓力、之下為支撐;同一價位跌破後會由支撐轉為壓力,因此不在偵測階段區分,而在判讀時依現價決定。計分只採計最接近的一個區,避免重複給分。

**為什麼用日線配 1 小時:** 高時框的價位累積了更多成交與時間,比低時框更受重視,兩者衝突時以高時框為準。時框太短則雜訊過多,到處都是「支撐」反而失去參考價值。日線抓主要區間、1 小時看價格接近時的反應,是搭配短線操作的標準組合。

**股票永續合約的限制:** MU/QQQ/MRVL/DRAM 追蹤的美股只在美東時間開盤,但合約 24 小時交易,其「日線」的起訖時點與美股收盤對不上。偵測到的擺動高低點仍是真實成交過的價格,但區間的分界不如 BTC/ETH 精確。

## 第三階段:量能確認(±1 分修正)

**只套用於 BTC/USDT 與 ETH/USDT**,且僅在前兩階段累計分數不為 0 時才生效。

成交量本身沒有方向性 —— 爆量可能是搶著買,也可能是恐慌賣。因此量能不當作獨立訊號,而是用來驗證價格訊號的可信度:

| 量能狀況 | 判定 | 效果 |
|---|---|---|
| 成交量 ≥ 均量 **1.5 倍** | 放量,量價配合 | 往原方向 **+1**(訊號加強) |
| 成交量 ≤ 均量 **0.7 倍** | 縮量,推力不足 | 向中性收斂 **1 分**(訊號減弱) |
| 介於兩者之間 | 量能普通 | 不調整 |

基準為過去 20 根 K 棒的平均成交量。

**範例:** BTC 因多頭排列取得 +1 分,但成交量僅均量的 0.37 倍,判定為縮量,分數削減為 0,最終標籤由「偏多」變為「中性」。

### 為什麼只套用在 BTC/ETH

股票永續合約追蹤的美股有開收盤時段,休市時成交量大幅萎縮。若用「過去 20 根 K 棒均量」當基準,等於把開盤與休市時段的量混在一起平均,結果會是:

- 開盤時段幾乎必然判定為「放量」
- 休市時段幾乎必然判定為「縮量」

那樣量能規則就不是在偵測異常量能,而是在偵測「美股現在有沒有開盤」,失去意義。BTC/ETH 為 24 小時連續交易,不存在此問題。

### 為什麼取已收盤的 K 棒

所有規則(價格與量能)一律使用**最後一根已收盤**的 K 棒,不使用仍在形成中的最新一根。

**量能方面**,未收盤 K 棒的成交量只累積了一部分,拿它跟完整 K 棒的均量相比會系統性地偏低,量能規則會退化成單向的「一律扣分」。

**價格方面**,未收盤 K 棒的「收盤價」其實是即時價格,會隨每一筆成交跳動。價格落在均線附近時,分數會在同一根 K 棒內反覆翻轉 —— 曾實際發生通知顯示 ETH 為 2 分,但使用者點開儀表板時已變成 0 分:當時價格 1917.64 與 EMA20 僅相距 0.02,隨後跌破均線,EMA 規則失效連帶使量能確認失效(量能僅在分數不為 0 時生效),兩分同時消失。

改用已收盤 K 棒後,訊號在該根 K 棒期間保持穩定,通知內容與稍後查看的儀表板一致。儀表板的「即時報價」卡仍顯示當前價格,但訊號判斷不受其影響;`evaluate()` 同時回傳 `price`(訊號依據的收盤價)與 `live_price`(即時價),兩者在介面上分開呈現。

## 分數對應標籤

| 分數 | 標籤 |
|---|---|
| ≥ +3 | 強烈做多 🟢🟢 |
| +1 ~ +2 | 偏多 🟢 |
| 0 | 中性 ⚪ |
| −1 ~ −2 | 偏空 🔴 |
| ≤ −3 | 強烈做空 🔴🔴 |

**分數範圍:** 股票標的為 ±5(四條價格規則 + 壓力支撐);BTC/ETH 為 ±6(額外的量能修正)。

## 通知規則

定義在 [check_signals.py](check_signals.py)。

滿足以下**兩個條件**才會發送 LINE 通知:

1. 分數絕對值 ≥ `ALERT_MIN_SCORE`(目前為 **2**,即需要兩條規則同時指向同一方向)
2. 該標的的訊號標籤與上次通知時**不同**

第二個條件是去重機制。訊號在同一根 K 棒內不會變,沒有去重的話同一個訊號會被重複推播,也會快速消耗 LINE 每月 200 則的免費額度。

### 狀態保存

狀態記錄在 `.alert_state.json`,由 GitHub Actions 的 cache 跨執行保存。未達門檻的標的會從狀態中移除,因此該訊號日後再次出現時仍會通知。

**狀態只在 LINE 送出成功後才寫入。** 若順序顛倒,發送失敗時(額度用罄、憑證過期、網路中斷)訊號會被記為「已通知」,下次執行因狀態未變而跳過,該則通知就永久遺失。目前的順序可確保發送失敗時下次自動重試。

`DRY_RUN=1` 模式完全不寫入狀態,避免測試污染正式狀態。

### 時框與門檻的取捨

回溯模擬各組合的通知量(已計入只在台灣 8–24 點檢查):

| 時框 | 門檻 | 每月估計通知 | 佔 LINE 免費額度 |
|---|---|---|---|
| 4h | 1 | 144 | 72% |
| 4h | 2 | 40 | 20% |
| 4h | 3 | 0 | 從不觸發 |
| 1h | 1 | 542 | **超量 271%** |
| **1h** | **2** | **117** | **58%**(目前設定) |
| 1h | 3 | 14 | 7% |

> 模擬取每個標的最近 200 根 K 棒。因此 4h 的觀察窗約 23 天、1h 約 5.8 天 —— 1h 的估計值取樣期間較短,可靠度低於 4h,實際用量仍需觀察。

1 小時時框搭配門檻 1 會超出 LINE 免費額度近三倍,因此改用 1h 時務必同時提高門檻。

選擇 `1h + 門檻2` 的理由:通知量與 `4h + 門檻1` 相近,但意義不同 —— 前者要求兩條規則同時認同,後者只需一條規則在較慢的時框上觸發。要求多條規則共識,過濾雜訊的效果比單純放慢時框更紮實。

**注意:** 門檻 3 幾乎不會觸發。回溯資料中四條規則從未有三條同時指向同方向,因此「強烈做多 / 強烈做空」標籤在實務上極少出現。若希望這兩個標籤有意義,需要重新設計計分方式(例如讓較強的訊號給 2 分而非 1 分)。

### LINE 免費額度

帳號使用「輕用量」方案,每月 200 則免費推播。額度用完後 API 會回傳錯誤、訊息不送達,**不會自動扣款**。

輕用量與中用量方案皆**無法加購訊息**,僅高用量(月費 NT$1,200 未稅、6,000 則)可按則加購。若通知量逼近上限,調高 `ALERT_MIN_SCORE` 遠比升級方案划算(門檻 3 的估計用量僅 14 則/月)。

## 可調參數

全部集中在 [config.py](config.py)。

| 參數 | 目前值 | 說明 |
|---|---|---|
| `SYMBOLS` | 12 個標的 | 儀表板顯示的完整清單 |
| `ALERT_SYMBOLS` | 6 個標的 | 其中會發 LINE 通知的子集 |
| `TIMEFRAME` | `1h` | K 線時框 |
| `DISPLAY_TIMEZONE` | `Asia/Taipei` | 顯示時區。交易所回傳 UTC,抓取後即轉換,故 K 線圖橫軸與所有時間標示皆為此時區 |
| `OHLCV_LIMIT` | 200 | 每次抓取的 K 棒數,需足夠 EMA50 等指標暖機 |
| `RSI_PERIOD` / `RSI_OVERSOLD` / `RSI_OVERBOUGHT` | 14 / 30 / 70 | RSI 參數與超買超賣門檻 |
| `EMA_FAST` / `EMA_SLOW` | 20 / 50 | 快慢均線期數 |
| `MACD_FAST` / `MACD_SLOW` / `MACD_SIGNAL` | 12 / 26 / 9 | MACD 參數 |
| `BB_PERIOD` / `BB_STD` | 20 / 2 | 布林通道期數與標準差倍數 |
| `VOLUME_MA_PERIOD` | 20 | 均量計算期數 |
| `VOLUME_SURGE_RATIO` | 1.5 | 放量判定倍數,調低則更容易加分 |
| `VOLUME_DRY_RATIO` | 0.7 | 縮量判定倍數,調高則更容易扣分 |
| `VOLUME_CONFIRM_SYMBOLS` | BTC、ETH | 套用量能確認的標的 |
| `SR_TIMEFRAME` / `SR_LOOKBACK` | `1d` / 120 | 壓力支撐所用的時框與根數 |
| `SR_PIVOT_WINDOW` | 3 | 前後各幾根都不越過才算擺動高低點,調大則區間更少更強 |
| `SR_CLUSTER_PCT` | 1.5 | 相距多少 % 以內的轉折點視為同一區 |
| `SR_MIN_TOUCHES` | 2 | 至少被測試幾次才算有效區間 |
| `SR_NEAR_PCT` | 1.0 | 現價距離區間多少 % 以內算「接近」,調小則更少觸發 |
| `SR_MAX_ZONES` | 6 | 最多保留離現價最近的幾個區 |
| `ALERT_MIN_SCORE` | 2 | 通知門檻,調高則通知變少 |

## 外觀

佈景設定在 [.streamlit/config.toml](.streamlit/config.toml),採淺色底搭配藍色強調色。多空語意色(綠 `#16a34a` / 紅 `#dc2626`)同時用於訊號標示與 K 線圖漲跌,`app.py` 上方的顏色常數與此檔對應,調整配色時兩處需一併修改。

## 本機執行

安裝依賴並啟動儀表板:

```bash
py -m pip install -r requirements.txt
py -m streamlit run app.py
```

單獨測試訊號檢查。`DRY_RUN=1` 只印出結果,不實際發送 LINE、也不寫入狀態:

PowerShell
```bash
$env:DRY_RUN="1"; py check_signals.py
```

bash / Git Bash
```bash
DRY_RUN=1 py check_signals.py
```

> Windows 上使用 `py`(Python Launcher)而非 `python`。預設的 `python` 可能指向 Microsoft Store 的轉接程式,執行時不會有任何輸出。

### 已知注意事項

- **GitHub Actions 內建排程不準時,故以 cron-job.org 為主要觸發來源。** 專案剛建立時內建 cron 完全不觸發(超過 11 小時、十餘個時段皆無),因而改由 cron-job.org 定時呼叫 GitHub API 的 `workflow_dispatch` 端點。內建排程後來自行恢復運作,但實測延遲多在 20–30 分鐘(排定 UTC 03:37 的執行落在 04:02、13:37 落在 14:07),符合 GitHub 文件所述「高負載時排程會延遲甚至丟棄」。目前兩個觸發來源並存,重複觸發不會造成重複通知(去重機制擋掉)。
- **修改 `app.py` 以外的檔案後,Streamlit Cloud 需手動 Reboot。** Streamlit 重跑 `app.py` 時不會重新載入已 import 的模組,新舊程式碼混用會產生 TypeError 之類的錯誤。
- **Binance 與 Bybit 封鎖雲端主機 IP**(451 / 403),故資料來源使用 OKX。
- **未使用 ccxt。** ccxt 抓資料前會載入交易所全部市場定義(OKX 逾四千個),記憶體開銷對 Streamlit Cloud 免費方案偏重,改為直接呼叫 OKX REST API。
